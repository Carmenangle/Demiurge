# v0.3 插件化设计 · 02 剧情推进管线（主战场）

> 用户诉求：剧情推进插件 = 添加角色卡、世界书、仓库的绑定按钮 + 剧情推进的整个链路可插拔。
> 难点自述：「剧情推进和表格 RAG 等内容环环相扣，没那么好拆分」。
> 本篇给出拆解方案：**不是把链路打散成碎片，而是把链路的三段顺序收敛成三个注册面，
> 数据依赖从隐式 ctx dict 变成显式 TurnLedger。**

## 一、现状事实（拆解对象）

### 1.1 链路本体（roleplay_node，agent_graph.py:667-990，约 1600 行）

```text
① 输入正则(placement 1, skip_depth_gated) :680
② 世界书检索 _resolve_worldbook :683（store 快照 → parse/schedule/assemble → 出 _world_rules）
③ 历史瘦身 story_history.last_story_round :700
④ 角色卡解析 _resolve_personas :705
⑤ 能动性预装配 _agency_prelude :717（AgencyDeps 容器，roleplay_agency.py:94-120）
⑥ 文风配置 prose_style.load_config :719
⑦ 阶段A 世界提案+规则裁判 _agency_propose :726（agency 纯规则裁判，非 LLM）
⑧ 预设组装 _resolve_preset :730（assemble_messages + select_chains + 采样参数）
⑨ 骰点规则注入 :769
⑩ 阶段B 生成上下文注入 :773-888（顺序硬编码）：
   RAG召回:778 → 表格检索:779 → 纪要召回:782 → 时间账本:801 → 认知库:816
   → continuity_compiler 四源编译:828 → directive:846 → 文风:850 → 视觉档案:856 → 表格只读:873
⑪ 宏替换/系统词/思维链/音频指令 :892-929
⑫ prompt_compiler.compile_messages :932
⑬ TurnFinalizationHooks 组装 :950-963（writeback/apply_output/anchor_offset/emit_ready/maintain）
⑭ roleplay_turn.execute_turn :964-986（回合事务核心，保持内核）
⑮ 异常兜底 :987-990
```

### 1.2 硬点（探查确认）

- **写回内联**：`_agency_writeback`（agent_graph.py:1325-1881，约 560 行）把状态写回、
  transition/illustration/audio 块提取、narrative_ci、插画 Profile 编译、视频请求编译全部内联。
- **维护顺序硬编码**：`_agency_maintenance`（:1964）表格:1971 → 认知:1972 → 纪要:1983 →
  Curator:1987 → style_review:1994，无注册点。
- **隐式轮间数据**：`_style_config`、`_world_rules`、`_continuity_facts/_continuity_beliefs`、
  `_agency_goal_deltas`、`_selected_persona_names` 等经 ctx dict 隐式传参（roleplay_node 内约定）。
- **产物白名单硬编码**：illustrate_recs/audio_recs 透传写死在 finalize_turn
  （roleplay_turn.py:456-507），新增插件产物类型需改白名单。
- **接缝已存在**：`TurnExecutionHooks/TurnFinalizationHooks`（roleplay_turn.py:99-133）五钩子
  全部可替换；`deps=None` 即整条子图缺席降级（:999）；各维护模块均有 gate 开关
  （gateBaseRate/curator_gate/fillEvery/prose_style.enabled/selfheal_attempts）。

### 1.3 环环相扣的真实依赖（为什么不能乱拆）

```text
主生成正文 ──┬→ 状态写回(character_state)      ← 吃正文 <状态更新> 块
             ├→ 表格维护(table_store)          ← 吃 用户输入+正文clean（不吃状态/纪要输出）
             ├→ 认知提取(belief_extractor)     ← 吃正文（纯规则）
             ├→ 纪要(narrative_store)          ← 吃正文+快照；产出后 → temporal_fact_store
             ├→ Curator(worldbook/RAG)         ← 吃本轮实际注入 index（来自②）
             └→ style_review                   ← 吃正文
下一轮读取 ──→ 表格只读/表行检索/纪要召回/时间账本/世界书 —— 全部是上一轮维护的产物
释放条件 ────→ 维护线程按 repo 锁串行完成，才允许同仓库下一轮（ARCHITECTURE.md:22）
```

**结论**：数据流向是清晰的 DAG，只是这个 DAG 没有被声明，而是长在函数体里。
插件化的本质 = **把 DAG 声明出来**。

## 二、设计：TurnPipeline 三段 + TurnLedger

### 2.1 TurnLedger（显式轮间数据容器）

```python
# services/turn_ledger.py（新，纯逻辑无 I/O）
class TurnLedger:
    """一个剧情回合内、组装与写回/维护各阶段之间的显式数据容器。
    键空间分两域：assembled_*（组装产物，只读给写回）与 derived_*（写回/维护产物）。
    每键声明 owner（插件 id）与 schema，读写越权在注册期校验。"""
```

迁移映射（现状 ctx 隐式键 → Ledger 键，全部登记进 API 面清单）：

| 现状隐式键（agent_graph.py） | Ledger 键 | owner（内置插件） |
|---|---|---|
| `_world_rules` :2815 | `assembled.world_rules` | worldbook-stage |
| `_style_config` :719 | `assembled.style_config` | prose-style-stage |
| `_continuity_facts` / `_continuity_beliefs` :801/:816 | `assembled.continuity_facts/beliefs` | continuity-stage |
| `_agency_goal_deltas` | `derived.goal_deltas` | agency-stage |
| `_selected_persona_names` | `assembled.personas` | persona-stage |
| 场景 `ctx["scene"]` | `assembled.scene` | supervisor（保留） |

规则：
- Ledger 是**每回合实例**，随回合结束归档进 run_trace（脱敏后），不跨回合持久——
  跨回合真源仍是各 store（character_state/table_store/narrative_store/…），不新增第二真源。
- 阶段间只许经 Ledger 键通信，禁止直接读 ctx 私有键（import-linter + code review 把关）。

### 2.2 三段 Stage 注册表（turn_pipeline.py）

```python
@dataclass(frozen=True)
class ContextStage:      # 对应现状 ①-⑫（阶段B 注入管线）
    id: str
    priority: int                    # 注入顺序，数值小先注入；同优先级按 id 稳定排序
    produces: tuple[str, ...]        # 写入的 Ledger 键
    requires: tuple[str, ...]        # 依赖的 Ledger 键（注册期做拓扑校验，缺依赖→拒载）
    run: Callable[[TurnContext], ContextBlock | None]   # None = 本轮缺席，静默跳过

@dataclass(frozen=True)
class WritebackStage:    # 对应现状 _agency_writeback 的各段
    id: str
    consumes: tuple[str, ...]        # 吃正文/哪些 Ledger 键
    produces: tuple[str, ...]
    run: Callable[[TurnFinalization, TurnLedger], TurnFinalization]  # 纯变换链

@dataclass(frozen=True)
class MaintenanceStage:  # 对应现状 _agency_maintenance 的各项
    id: str
    band: str                        # "immediate"（同回合必须完成）| "background"（可延迟）
    requires: tuple[str, ...]        # 依赖的 derived_* 键 → 执行期拓扑排序
    gate: Callable[[TurnLedger], bool] | None   # 频率/开关门控（fillEvery 等迁入）
    run: Callable[[MaintenanceContext], None]
```

**组装管线（assemble）**：现状 ①-⑫ 拆为约 10 个内置 ContextStage（input-regex、
worldbook、story-history、personas、agency-prelude、preset、world-proposal、continuity、
style、tables-readout）。`priority` 现值直接照抄现状顺序（20,30,40,…），行为不变。
产物 = 有序 `ContextBlock` 列表 + Ledger，最终仍汇入 `prompt_compiler.compile_messages` ——
**prompt_compiler 的位置合同不动**（ARCHITECTURE.md:63），插件只能贡献内容块，
不能决定消息位置。

**写回管线（writeback）**：`_agency_writeback` 拆为约 8 个 WritebackStage（think-split、
transition-extract、illustration-extract、audio-extract、status-writeback、table-block-clean、
narrative-ci、scene-illustration-plan）。按注册顺序形成纯变换链，输入输出都是
`TurnFinalization`，任意一段异常按现状语义失败关闭（不吞、不把控制块回退前端）。

**维护管线（maintenance）**：`_agency_maintenance` 拆为 6 个 MaintenanceStage
（table-maint、belief-maint、chronicle-maint、curator-maint、style-review、temporal-fact）。
`requires` 声明依赖（chronicle→temporal_fact），执行期拓扑排序替代硬编码顺序；
**immediate band 全部完成前不释放同仓库下一轮**（沿用现有 repo 锁语义，agent_graph.py:1941）。

### 2.3 主生成保持内核

`roleplay_turn.execute_turn/finalize_turn` **不插件化**：正文完整性与自愈
（`ensure_complete_visible_content`/`_selfheal_loop`）、发布顺序（writeback→正则→安全网→
emit_ready→maintain）是回合事务合同，属核心（ARCHITECTURE.md「剧情回合事务」条）。
插件接触点只有三个 hook 槽（generate/apply_output/maintain），与现状一致。

### 2.4 剧情推进插件 = 一份 manifest 捆绑全部贡献

```jsonc
{ "id": "story-progression",
  "contributions": [
    { "kind": "agent_route", "route": "roleplay", "node_ref": "...", "requires_card": true },
    { "kind": "turn_stage", "phase": "assemble",    "stage": { "id": "worldbook", ... } },
    { "kind": "turn_stage", "phase": "assemble",    "stage": { "id": "continuity", ... } },
    { "kind": "turn_stage", "phase": "writeback",   "stage": { "id": "status-writeback", ... } },
    { "kind": "turn_stage", "phase": "maintenance", "stage": { "id": "chronicle-maint", ... } },
    { "kind": "binding_ui", "target": "repo_bindings",
      "fields": [
        {"key": "card_names",        "widget": "card-picker",   "multi": true},
        {"key": "opening_card_name", "widget": "card-picker",   "multi": false},
        {"key": "worldbook_name",    "widget": "worldbook-picker"},
        {"key": "persona_id",        "widget": "persona-picker"}
      ] }
  ] }
```

- **绑定按钮的插件化**：现状绑定是前端存 `cardName/worldbookName/personaId` + 后端解析
  （ARCHITECTURE.md:558）。BindingContribution 声明绑定字段（key/widget/校验），
  前端绑定面板按注册表渲染（04 篇），后端 `agent_request_context` 按声明字段收参——
  加第四种绑定（如「预设包绑定」「画布模板绑定」）= 注册一个 binding_ui 贡献，不改面板本体。
- **另一个剧情推进插件怎么共存**：多插件同时贡献 `agent_route: roleplay` 冲突——规则：
  route 唯一，后注册者拒载并提示；想换推进风格 → 贡献新 route（如 `roleplay-strict`），
  supervisor 可路由到，或用户在 Agent 设置里把 roleplay 的实现切到别的 Provider（同 route
  单选，落 user_state）。**管线 stage 不独占**：第三方插件可往三段各追加 Stage
  （如"每回合自动写文风诊断"→ maintenance band 加一个 stage），这是插件化最大的收益点。

## 三、错误语义与降级（沿用并显式化）

| 情形 | 行为 |
|------|------|
| Stage 抛异常 | assemble：该 Stage 跳过 + trace `stage.failed`，其余继续（现状各召回本就失败降级）；writeback：失败关闭（现状语义，控制块不得泄漏前端）；maintenance：该 Stage 失败其余继续（现状逐项隔离） |
| requires 的 Ledger 键缺失 | 执行期跳过 + trace，不重试不猜 |
| 整个剧情推进插件禁用 | route 从注册表消失 → supervisor 语义分派回 answer；这正是「插件缺席 = 降级」不变量 |
| 第三方 Stage 与内置 priority 冲突 | 合法（允许插队注入），但 token 预算由 continuity_compiler 归口，超预算按其既有裁剪规则 |
