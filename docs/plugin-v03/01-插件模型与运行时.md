# v0.3 插件化设计 · 01 插件模型与运行时

## 一、PluginManifest（唯一身份真源）

每个插件一个 `plugin.json`（内置插件由代码内 `PluginManifest(...)` 等价声明）：

```jsonc
{
  "id": "story-progression",          // 全局唯一，[a-z0-9-]
  "version": "0.3.0",
  "api_version": 1,                    // PLUGIN_API_VERSION，核心升级时旧插件拒绝加载并提示
  "label": "剧情推进",
  "description": "角色卡/世界书绑定与剧情回合推进链路",
  "source": "builtin",                 // builtin | user | external
  "permissions": [                     // 声明制，最小化；见 §四
    "capability:file.read_text",       //   需要的能力
    "needs_model:chat",                //   需要的模型档位
    "turn_stage:assemble",             //   需要注册的管线段
    "view:chat.panel_card",            //   需要的前端贡献面
    "data:repo_bindings"               //   需要读写的作品数据域
  ],
  "contributions": [ /* 按 kind 判别的贡献点数组，见 §二 */ ]
}
```

**规则**：
- manifest 是声明面，实现是代码面；`scripts/generate_plugin_manifest.py` 从内置插件导出
  `backend/app/generated/plugin_manifest.json`，`--check` 进 CI 门禁（照抄 capability_manifest 模式，
  scripts/generate_capability_manifest.py:25-45）。
- `permissions` 与实际 `contributions` 交叉校验：贡献了 `turn_stage` 却没声明对应 permission → 拒载。
- 内置插件 `source="builtin"` 权限校验只警告不阻断（迁移期）；`user/external` 强制。

## 二、贡献点（Contributions）判别联合

```python
Contribution =
  | {kind:"agent_route",   route, node_ref, tools:[str], model_pref, ...}   # Agent 插件
  | {kind:"capability",    capability: Capability}                          # 能力插件（复用现有 dataclass）
  | {kind:"agent_loop",    name, provider_ref}                              # 循环插件
  | {kind:"media_renderer",kind:"image|video|audio", format, factory_ref}   # 媒体插件
  | {kind:"turn_stage",    phase:"assemble|writeback|maintenance", stage}   # 管线插件（02 篇）
  | {kind:"data_pack",     pack_type:"preset|regex|worldbook|character"}    # 数据插件（05 篇）
  | {kind:"binding_ui",    target:"repo_bindings", fields:[...]}            # 剧情绑定按钮（02 篇）
  | {kind:"view",          view_key, entry, nav:{...}}                      # 视图插件（04 篇）
  | {kind:"ui_decl"}       声明式 UI 贡献（04 篇，无代码）
```

`*_ref` 字段一律 `"模块:函数"` 格式，加载器 importlib 验证可导入可调用（复用
capability_registry.validate_handlers 的既有模式，capability_registry.py:98）。

**设计决策：外部插件的前端部分只允许 `ui_decl` 声明式贡献**（导航项、设置卡、按钮、
面板卡片、文案图标），不允许指向任意 JS 模块。原因：前端无进程沙箱，任意外部 JS 等于
放弃全部安全边界；内置视图插件（ChatView/Canvas）是源码内代码，走正常构建与测试门禁。
此决策让 6（视图）类插件天然分两级：内置 = 代码级，外部 = 声明级。详见 04 篇 §四。

## 三、加载器与生命周期

`services/plugin_runtime.py`（新，注册表属主，≈200 行）：

```text
load_all():
  1. 注册内置插件：import services.builtin_plugins 包，模块尾 register_plugin(manifest, registry)
     —— 编译期确定，随源码发布，随 pytest 门禁。
  2. 扫 DATA_DIR/plugins/*/plugin.json：
     a. 读 manifest → api_version 校验 → 权限交叉校验 → 哈希校验（06 篇）
     b. importlib 加载插件入口模块（若含代码）
     c. 逐贡献点注册到对应注册表（§四）
     d. 任何单插件失败：记 plugin.load_failed Trace + 设置页显示，**不影响其他插件与核心**
  3. 快照 PluginRegistry 状态（含禁用清单 DATA_DIR/plugins/disabled.json）
```

生命周期：`enabled / disabled / failed(原因) / incompatible(api_version)` 四态，设置页可视；
禁用 = 从注册表摘除全部贡献点（幂等），**不删文件**。热重载仅限数据插件（preset/regex
热读已成立，preset_store 无需重启）；代码插件注册后提示重启（沿用 RunContext 改动需重启的
现有惯例）。

## 四、注册表落点（每类一个属主）

| 注册表 | 属主模块 | 现状 → 目标 |
|--------|---------|------------|
| AgentRouteRegistry | `agent_plugins.py`（原地扩展） | AgentPlugin 加 `node_ref: str`、`tools: list[str]`、`loop: str` 字段；register 校验 node_ref 可导入。agent_graph 路由表与条件边**都**从注册表生成（现状两处硬编码，agent_graph.py:179-181 + :2292-2301 是 v0.3 必须合流的点） |
| CapabilityRegistry | `capability_registry.py`（不变） | 15 条内置照旧；外部能力经 PluginRegistry 代注册，自动带 `source` 标记进 manifest |
| MediaRendererRegistry | `media_renderers.py`（新，收编 scene_illustration 注册表） | 见 03 篇 |
| TurnStageRegistry | `turn_pipeline.py`（新） | 见 02 篇 |
| ViewRegistry | `frontend/src/lib/viewRegistry.tsx`（新） | 见 04 篇 |
| DataPackRegistry | `plugin_runtime.py` 内置段 | 见 05 篇 |

**import-linter 新合同**（随 M0 落地）：
- `plugin_runtime` 不得 import 任何业务 services（只做装载与校验）；
- 业务 services 不得 import `plugin_runtime`（注册由 builtin_plugins 包单向进行）；
- 各注册表之间互不依赖。

## 五、权限模型

权限词法 = 三域并集，全部映射到**既有** enforcement 点，不新建沙箱：

| 权限 | enforcement（现状） |
|------|--------------------|
| `capability:<operation>` | AgentPlugin.tools 子集过滤（M1）+ fabric_loop 审批闸门照旧 |
| `needs_model:<档位>` | capability_registry.with_availability 的 needs_model 既有机制 |
| `turn_stage:<phase>` | TurnStageRegistry 注册时校验 |
| `view:<面>` | ViewRegistry/ui_decl 渲染时校验 |
| `data:<域>` | 数据插件安装目标目录白名单（presetDir / regex / repo 绑定字段），越界拒绝 |

外部插件默认权限 = **空**：未声明的能力一个都拿不到；`run_shell`、`file.write_text`、
联网类能力对外部插件**默认拒绝**（declared 也要在安装 UI 二次确认，06 篇）。
instruction_provenance 的低权限外部内容标记继续适用于插件自带提示词/技能文本。

## 六、版本与兼容

- `PLUGIN_API_VERSION=1`；核心升级 api_version 时：manifest 不匹配 → `incompatible` 态，
  设置页提示，不阻断其余加载。
- 兼容承诺：内置贡献点的**注册 schema** 向后兼容一个 minor；TurnLedger 键、ContextBlock
  字段、media renderer 接口是 API 面，改动需在 07 篇迁移表登记。
- 旧 `DATA_DIR/agent_plugins.json`（元数据覆盖）继续支持一个版本周期，语义并入新 manifest
  的 `overrides`，双读期后废弃。

## 七、与现有三注册表的关系（不推倒）

- `agent_plugins.py` / `capability_registry.py` / renderer dict **原样保留为各域注册表**；
  PluginRegistry 是它们之上的**装载器与权限层**，不是替代品。这样 M0 迁移成本近零，
  且每个域的既有测试与 manifest 门禁继续生效。
